# PLAN-A-00-111126 — Flutter migration and production readiness

| | |
|---|---|
| Plan | A, revision 00 |
| Date | 2026-11-11 |
| Status | Proposed. No migration work has started. |
| Scope | Rebuild BaoBao in Flutter for Android and iOS, and raise it from prototype to a releasable product. |
| Inputs | `PROJECT-SPECS.md` (behaviour and known problems), `CODEMAP.md` (current code) |

This is a **rebuild with content reuse**, not a line-by-line port. The dialogue, voice clips, art, rules, and visual style carry over. The Activity-and-singleton structure does not.

## 1. Goals and non-goals

### Goals

1. Feature parity with the Kotlin prototype (`PROJECT-SPECS.md` §2) on Android and iOS from one codebase.
2. The intervention flow keeps working and is covered by tests. It was unreachable in the prototype until the 2026-11-11 fix (`LOG.md`).
3. Every problem in `PROJECT-SPECS.md` §5 is fixed or explicitly accepted.
4. The app can pass Google Play and App Store review for a health-adjacent app.
5. Content (dialogue, catalogue, helplines) can be changed without touching code.

### Non-goals for this plan

- Cloud accounts, sync, or backup.
- Free-text or generated conversation.
- New features beyond parity (mood history charts, reminders, more games). These are listed in section 12 as follow-ups.
- Web or desktop builds.

## 2. Decisions

Use the latest stable release of each tool at the moment Phase 0 starts, then pin exact versions in `pubspec.lock`. No versions are fixed in this document on purpose.

| Concern | Choice | Why |
|---------|--------|-----|
| Framework | Flutter, stable channel, Dart with sound null safety | One codebase for Android and iOS. |
| Architecture | Feature-first folders; three layers per feature (presentation → application → domain), with a shared data layer | Keeps rules out of widgets, which is the prototype's main structural flaw. |
| State management and dependency injection | Riverpod (with code generation) | Compile-safe providers, easy overrides in tests, no global singletons. |
| Navigation | `go_router` | Declarative routes, redirect guards for onboarding and lock state. |
| Models | `freezed` + `json_serializable` | Immutable value types and JSON parsing for content files. |
| Local database | `drift` on SQLite, encrypted with SQLCipher | Typed queries, **real versioned migrations with tests**, encryption for mood data. |
| Small settings | `shared_preferences` | Volumes, flags. Nothing sensitive. |
| Secrets | `flutter_secure_storage` | Holds the database key (Keychain / Keystore). |
| Audio | `just_audio` + `audio_session` | Three independent channels (music, effects, voice), ducking, interruption handling. |
| Claw machine | Plain Flutter: a pure-Dart game model driven by a `Ticker`, drawn with `CustomPainter` | The game is simple. A testable model matters more than an engine. Adopt Flame only if this proves limiting. |
| Localisation | `flutter_localizations` + ARB files with `gen-l10n` for UI text; per-locale JSON for dialogue | No hard-coded strings. |
| External links | `url_launcher` | Dial, text, and web links on the resources screen. |
| Haptics | Flutter `HapticFeedback` | Removes the need for the `VIBRATE` permission. |
| Splash and icons | `flutter_native_splash`, `flutter_launcher_icons` | Generated, consistent across platforms. |
| Lint | `flutter_lints` as the base, plus stricter rules in `analysis_options.yaml` | Enforced in CI. |
| Tests | `flutter_test`, `mocktail`, golden tests, `integration_test` | See section 9. |
| CI | GitHub Actions | Format, analyse, test, and build on every pull request. |
| Crash reporting | Sentry, **opt-in**, with all personal and mood data stripped | Needed to run a production app; must not leak sensitive data. |

### Accounts (recommended default for open decision 1)

Replace username/password accounts with **local profiles**:

- One device can hold several profiles, each with a display name.
- No passwords. A password on unencrypted local data protects nothing, and forgotten passwords cannot be recovered without a server.
- Optional app lock using the device's biometrics or PIN (`local_auth`).
- "Guest" becomes simply the default first profile.

If the owner decides to keep passwords, store them with Argon2id and a per-user salt, and never display other accounts.

### Existing user data

The prototype was never published and uses the placeholder ID `com.example.baobao`. The Flutter app gets a new application ID, so it installs fresh. **No migration of Room data is planned.**

## 5. Data model

All tables except `profiles` carry `profile_id` with cascade delete.

| Table | Columns | Replaces |
|-------|---------|----------|
| `profiles` | id, display_name, created_at, last_active_at | `user_data` credentials |
| `wallets` | profile_id, balance | `user_data.currency` |
| `mood_entries` | id, profile_id, mood, weight_delta, created_at | `user_data.moodHistory` JSON string |
| `emotional_state` | profile_id, weight, consecutive_negative, last_intervention_at | Four `user_data` columns |
| `owned_items` | profile_id, item_id, acquired_at | Comma-separated lists and the unscoped `purchases` table |
| `selections` | profile_id, slot (music/outfit/background), item_id | `user_data.selected*` |
| `transactions` | id, profile_id, amount, reason, created_at | New: an audit trail for currency |
| `conversation_progress` | profile_id, mood, last_node_id, path, updated_at | `user_data.currentConversationPath` |
| `claw_state` | profile_id, tries, next_refill_at, purchases_today, purchases_date | SharedPreferences |
| `claw_stats` | profile_id, plays, wins, earnings, best_win | SharedPreferences |

Rules:

- Spending and granting currency happen in a single database transaction together with the `owned_items` or `claw_state` change.
- Schema version starts at 1. Every later change ships with a migration and a migration test against a stored schema snapshot. Destructive fallback is never enabled.
- The database is encrypted. The key is generated on first run and kept in secure storage.
- Android backup is disabled for the database, or restricted to encrypted device-to-device transfer.

## 6. Content format

Conversation file (one per mood per locale):

```json
{
  "mood": "sad",
  "start": "sad_start",
  "nodes": {
    "sad_start": {
      "line": "…",
      "voice": "s_sad_01",
      "emotion": "sad",
      "nudge": null,
      "loopPoint": false,
      "options": [
        { "text": "…", "next": "sad_talk", "moodEffect": 0 }
      ]
    }
  }
}
```

`tool/validate_content.dart` runs in CI and fails the build when:

- an option's `next` is not a node ID or a reserved target (`return_to_mood`, `show_resources_screen`);
- a node is unreachable from `start`, or a tree has no loop point reachable from every node;
- a `voice` value has no matching audio file, or an audio file is referenced by nothing;
- a catalogue item references a missing asset;
- a locale is missing a key that the base locale has.

## 7. Phases

Estimates are rough working days for one developer and are not commitments. Phases 1–3 can overlap; Phase 5 features can be built in parallel once Phase 4 is done.

### Phase 0 — Foundations (3–5 days)

1. Get answers to the open decisions in section 11.
2. Move the Kotlin app to `legacy/android-native/` and confirm it still builds there.
3. Create the Flutter project at the repository root with the final application ID.
4. Add lint rules, formatting, and the folder skeleton from section 3.
5. Add CI: format check, `flutter analyze`, `flutter test`, Android debug build, iOS build without signing.
6. Add build flavours `dev` and `prod`.
7. Update `README.md`, `CODEMAP.md`, and `LOG.md`.

**Exit:** an empty themed app runs on an Android emulator and an iOS simulator; CI is green; the Kotlin app still builds from its new location.

### Phase 1 — Content and assets (5–8 days)

1. Write `tool/extract_content` to turn `ConversationManager.kt`, the `VoiceManager.kt` node-to-clip maps, `TutorialManager.kt`, and the shop prices into the JSON files in section 6. Review the output by hand against the Kotlin source.
2. Write `tool/validate_content.dart` and add it to CI.
3. Copy voice clips. Check that the `.aac` files play on iOS through `just_audio`; if any do not, repackage them all as `.m4a` without re-encoding.
4. Resolve the music licence question. Replace any track without a confirmed licence.
5. Convert character art and large PNGs to WebP at appropriate resolutions. Convert XML shape drawables that are worth keeping to SVG or rebuild them as widgets.
6. Register all five Quicksand weights correctly.
7. Build `helplines.json` with at least the launch countries and an international fallback. Have every entry checked by a person against the organisation's own website.

**Exit:** all content loads from assets in a unit test; the validator passes; total asset size is recorded and lower than the prototype's.

### Phase 2 — Core domain (5–7 days)

Pure Dart, no Flutter imports, developed test-first.

1. `MoodTracker`: records a check-in, applies the weight table, maintains the consecutive-negative counter.
2. `InterventionPolicy`: threshold, pattern, cooldown, and reset rules from `PROJECT-SPECS.md` §2.4, using an injected clock.
3. `ConversationEngine`: start node selection (mood tree or intervention tree), option handling, loop points, reserved targets, mood effects.
4. `Wallet` and `Catalogue`: balance rules, purchase preconditions, ownership.
5. `ClawTries`: refill maths, daily purchase limit, date rollover, clock changes.
6. `ClawGame`: state machine, movement, hit test in normalised coordinates, prize generation with an injected random source, combo multiplier.

**Exit:** at least 90% line coverage on `domain/` folders; a test proves that the sequence anxious, anxious triggers the intervention and that a repeat within 24 hours does not.

### Phase 3 — Data layer (4–6 days)

1. drift schema from section 5, encrypted, with key management.
2. Repositories per feature, exposed as Riverpod providers, returning streams where the UI needs live values.
3. Atomic purchase and reward operations.
4. Migration test harness with the version 1 schema snapshot.
5. Profile deletion that removes all of that profile's rows ("delete my data").

**Exit:** repository tests pass against an in-memory database; a test confirms two profiles have independent wallets, items, and claw state.

### Phase 4 — App shell (5–7 days)

1. Theme: colour scheme from the existing palette (tan `#CAAD7E`, cream `#ECEBC9`, off-white `#F6F6DB`, greens `#D5E7B8` / `#C4DEA4` / `#A7D489`), typography, bamboo component styles, with contrast checked against WCAG AA.
2. Shared widgets: `BambooButton`, `SpeechBubble`, `TypewriterText`, `CharacterView`, `LoadingOverlay`, dialog scaffold (see `docs/legacy/DIALOG_DESIGN_STANDARD.md`).
3. Router with guards: first run → onboarding; locked → unlock; otherwise home.
4. Audio services: music follows the current screen and selection; voice interrupts voice; music ducks under voice; everything pauses when the app is backgrounded or a call arrives.
5. Onboarding: disclaimer ("not a substitute for professional care"), privacy summary, age confirmation, profile creation, optional app lock.
6. Localisation scaffolding with English as the base locale.

**Exit:** a user can install, complete onboarding, and land on a home screen with music and a greeting; golden tests cover the shared widgets.

### Phase 5 — Features (15–22 days)

Build in this order; each item includes widget tests.

1. **Mood check-in and conversation.** Check-in sheet, conversation UI with typewriter text and voice, choices, feature nudges, loop back to idle. Recording the check-in is part of this item.
2. **Intervention and resources.** Intervention tree, country-aware resources screen, dial/text/web actions with a fallback when the device cannot perform one. A permanent "Get help" entry in settings that does not depend on the trigger.
3. **Home.** Status bar (balance, mood, tries), quick actions (joke, affirmation, self-care), time-based greeting.
4. **Shop and customisation.** Catalogue-driven shop, purchase confirmation, selection of outfit, background, and music with live preview.
5. **Settings.** Volumes, voice on/off, reduced motion, text size follows the system, app lock, profile switch and delete, privacy controls, licences, tutorial replay.
6. **Tutorial.** Content-driven steps.
7. **Claw machine.** Painter and controller on top of the Phase 2 model; tries display and timer; purchase of tries; result feedback with haptics and voice.

**Exit:** every behaviour in `PROJECT-SPECS.md` §2 is demonstrated on both platforms; an integration test walks sign-in → check-in → conversation → claw win → purchase → equip.

### Phase 6 — Production hardening (8–12 days)

1. **Accessibility:** semantic labels on every control and image, logical focus order, 48 dp touch targets, text scaling to 200% without clipping, reduced motion honoured, an alternative to press-and-hold in the claw machine, tested with TalkBack and VoiceOver.
2. **Performance:** cold start under 2 seconds on a mid-range Android device, no dropped frames in the claw machine in profile mode, images pre-cached, app size measured and budgeted.
3. **Reliability:** global error handling, opt-in crash reporting with data scrubbing, graceful handling of missing audio and low storage.
4. **Privacy and compliance:** privacy policy, in-app data deletion, Google Play Data safety form, App Store privacy labels, content rating, review of each store's health-app policies, clinical wording reviewed by a qualified person.
5. **Security:** release signing set up outside the repository, code shrinking and obfuscation on, dependency licence and vulnerability check in CI, no secrets in the repo.
6. **Localisation:** all UI text in ARB files; second locale added if in scope.
7. **Release engineering:** versioning scheme, changelog, tagged builds from CI, store listing assets.

**Exit:** the checklist in section 10 is complete.

### Phase 7 — Release and retirement (ongoing, 3–5 days of work)

1. Internal testing track and TestFlight.
2. Closed beta with a feedback channel; fix what it finds.
3. Staged production rollout with crash-free rate monitored.
4. Delete `legacy/android-native/` and `docs/legacy/` once the Flutter app is in production; update all docs.

**Exit:** the Flutter app is live on both stores and the Kotlin code is gone from the default branch.

## 9. Testing strategy

| Level | What it covers | Target |
|-------|----------------|--------|
| Unit | All `domain/` code, content parsing, repositories on an in-memory database | ≥ 90% of domain lines |
| Content validation | Graph integrity, asset references, locale completeness | Runs on every pull request |
| Migration | Each schema version upgrades to the next without data loss | One test per version step |
| Widget | Each screen's states: loading, empty, normal, error | Every screen |
| Golden | Shared widgets and key screens at 1.0× and 2.0× text scale | Shared widgets + five key screens |
| Integration | The main journey and the intervention journey on an emulator | Two flows, run in CI nightly |
| Manual | Screen readers, real-device audio interruptions, both platforms | Before each release |

Time-dependent rules (cooldown, refills, greetings, daily limits) always use the injected clock so tests never wait or depend on the real time.

## 10. Production readiness checklist

- [ ] Intervention triggers correctly and is covered by automated tests

## 12. Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| Store rejection under health-app policies | Blocks release | Disclaimer, verified helplines, no medical claims, policy review in Phase 6 before submission |
| Music cannot be licensed | Lose current soundtrack | Decide in Phase 0; budget time for replacements in Phase 1 |
| Voice clips do not play on iOS as-is | Silent conversations on iOS | Test in Phase 1; repackage to `.m4a` |
| Content extraction introduces errors in dialogue | Wrong or broken conversations | Validator in CI plus a manual read-through of every tree |
| Claw machine feels worse than the original | Engagement feature regresses | Tune against a recording of the Kotlin version; keep the model's constants in one place |
| App size grows with a second locale's voice clips | Larger download | Compress audio; consider downloading voice packs later |
| Scope creep into new features | Parity slips | New features wait until after Phase 7 |
